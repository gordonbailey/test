The problem

A UTM tag is the label a marketer puts on a link so they can tell which ad or email brought in a donation. GoFundMe Pro dropped them. Some pages captured the tags, nothing saved them onto the donation, and nothing showed them in reporting — so a nonprofit could not tell which campaign raised the money.

Customers said so five times in feature requests. IRUSA, Stand Up To Cancer, Feed My Starving Children and West Virginia University all asked for it. Every major competitor already has it. Agencies were hand-matching Google Analytics against our reports to fill the gap.

The research found the same thing on its own. The interviews turned up Feed My Starving Children unable to export the tags in its own links, tags dropping during peer-to-peer setup, and 96% of Salvation Army donations arriving with no source at all.

What was done

The original ticket covered everything at once and no team could schedule it. It was split in two: catch and save the tags, then show them in reporting. Before either, someone had to prove where the tags were actually being lost.

Where the tags were being lost

Reading the code suggested one leak. Running real donations through with test tags attached found two.

Studio

The tags were caught on arrival and carried through every step of the donation form. Then the final submission left them out. Every tag reached analytics and none reached the donation record — which is why this looked fine from the outside.

Embedded donation forms

When the form is embedded in a nonprofit's own website, a tag has to survive ten handoffs between the page, the frame and the app. All ten worked, including the one an engineer had called "hacky" — which is what put it on the list to check.

The decision worth knowing

The tags are not stored on the donations table. They live in a new separate table that points at each donation. The donations table is too big to change — adding columns would have locked the database for around 48 hours. That one constraint shapes everything after it, including the unfinished commerce path below, which writes to the old table and so never reaches the new one.

Two open decisions have since been settled

Resolved

Yes to the public API, but you have to ask for it

Shipped in PR #1484. Developers have to request the tags rather than getting them by default, because including them automatically would slow down every single donation lookup. Signed off by Mai.

Resolved

Keep the reporting plain

Both agencies said the same thing: they want GoFundMe to be clean data they can export, not another charting tool. So the tags are optional columns, off by default, sitting alongside the old source fields rather than replacing them. Most donations have no tags, so the empty state was designed carefully — otherwise the report looks broken.

What it does not cover

Nothing tests that the tags survive embedded forms

A test was specified — put a donation through and check all five tags come out the other end, naming whichever handoff dropped them. It was closed without being built when the storage design changed. Until it exists, four files can be edited in ways that silently break attribution on embedded forms. The test was written and syntax-checked but never pushed.

One donation path still loses the tags, and a customer is waiting

Designations write to the old table, so the tags never reach the new one. IRUSA is the named customer. Open between Shiran and Tony.

Two old tickets are stale rather than closed

PRO-2098 and PRO-5251 both sit open although the work moved past them. Not a delivery risk, but the kind of thing that makes a board unreadable a year later.

Five tags only, and no attribution model

This delivers the raw tags on each donation. It does not decide which one gets the credit when a donor arrives twice, and it does not cover Google or Facebook click IDs. Peer-to-peer is out of scope for now.

Nobody is measuring whether customers tag their links at all

The whole feature is worthless to a nonprofit that never tags anything, and there is no tracker for that.
