The problem

The customer evidence was unambiguous: five CFBR feature requests (575, 654, 857, 881, 894) calling native UTM table stakes; enterprise customers unable to attribute revenue to channel, including IRUSA, Stand Up To Cancer, Feed My Starving Children and West Virginia University, plus at-risk accounts FFTP, ACS and Shatterproof. Every major competitor ships it. Agencies were spending hours reconciling Google Analytics against Classy reports with brittle hacks.

Research found the same thing independently. The interview synthesis found FMSC unable to export the UTM parameters in its own tracking links, source codes dropping during P2P setup and at site boundaries, and 96% of Salvation Army transactions carrying no referral data. Both agency consultations, Community Boost and Blue State, named the same unlock: UTM in self-serve reporting plus CSV off first-party data.

What was done

The original all-in-one epic (PRO-5251) was too big to schedule, so it was split along the natural team boundary: capture and persist in one epic, surface in reporting in another. A spike ran first to replace a static code audit with runtime proof.

What the spike found

The static audit said UTMs were missing from one submission body and present in the other. The spike loaded real checkouts with ?utm_source=test&utm_medium=cpc&utm_campaign=spike and confirmed both drop points in the network tab.

Studio — the drop point

UTMs were captured at landing, persisted across the multi-step flow in sessionStorage, and reached mParticle as campaign_* properties, but were not in the donation submission payload. FinalizeOrderArgs omitted them. Every UTM reached analytics and none reached the transaction record.

EG3 — the ten-hop chain

Parent URL → nav._getAllParams → iframe src= → DONATION_PARAMS_UPDATE postMessage → modal-app Redux → wire body. Every hop worked at runtime, including the inline-grid launcher whose implementation had been described as "hacky", which is what put it in scope.

The architecture decision worth knowing

UTM does not live on the transactions table. It persists in a new related tracking model on APIv2 — a separate table with five UTM fields and a foreign key to the transaction. The transactions table is too large to alter: a schema migration would have blocked the database for roughly 48 hours. That one constraint shapes everything downstream, including the commerce write path, which does not reach the new table through its existing "as-is" passthrough metadata and therefore needs explicit work.

Two open decisions have since been settled

Resolved

Public API for V1 — yes, opt-in

Read-only UTM exposure shipped in PR #1484, verified against the deployed dev API and cross-checked against the dev DB. Delivery is opt-in, because auto-including the utm object would force a join on every transaction read. It piggybacks on the existing ?with=source_tracking_codes request and returns a stable five-key shape with nulls for anything not captured. Signed off by Mai in #proj_e2e_utm_support_gfmpro.

Resolved

Reporting design — deliberately plain

Both agencies were explicit that GoFundMe should be a clean data source rather than a charting tool. So "UTM Parameters" sits under Property → Marketing beneath the existing Source Parameters group. Columns are select-only and off by default, ordered after the legacy Source Code and Referrer columns so the two coexist. Free-text "contains" matching as well as selection, and CSV and saved reports both inherit the selection. Most donations are untagged, so empty states were designed so reports do not look broken.

What it does not cover

No end-to-end test for the ten-hop chain

PRO-5697 specified one: a fixture-driven test asserting all five UTM keys reach the postMessage payload and the /finalize-order wire body across both modal-launch paths, failing with the name of the hop that dropped. It was closed Won't Do once the APIv2 architecture changed the shape of what needed testing, with coverage deferred until the frontend UI ticket lands. Until then, any change to nav.ts, modal.ctrl.ts, modal.view.ts or the modal-app URL parser can silently break EG3 attribution. A jest spec was written and syntax-checked but never pushed.

The commerce write path is unfinished, with a named customer

UTM lands in a new table commerce does not write to, so the existing passthrough metadata never reaches it. Designations, IRUSA's use case, are the concrete example. Open between Shiran and Tony.

Multiple source-tracking-code records, cause unknown

Which UTM record to return when several exist is still open, and nothing in the tickets resolves the cause.

Two predecessor tickets are stale rather than closed

PRO-2098 sits in To Do although PRO-6771 realized it, and PRO-5251 sits in Backlog although both its child epics have moved past it. Not a delivery risk, but the kind of residue that makes a board unreadable a year later.

Phase 1 only: five parameters, no click IDs

Scope is the five utm_* parameters. The original epic also wanted gclid, fbclid and other click IDs, which did not make Phase 1. Fundraise (peer-to-peer) was out of scope pending re-assessment.

Which reporting build tickets shipped is not visible from here

PRO-6748 proposed five child stories: design, Transaction History columns and CSV, filtering, saved reports, empty states. Only design appears on the slide and the epic is now closed, so whether the rest shipped, merged elsewhere or closed with the epic cannot be told from these twelve tickets.

No attribution model, and no measurement of adoption

This delivers raw parameters on transactions. First-touch versus last-touch, new-versus-existing donor attribution, recurring attribution and cross-domain stickiness are all the future phase. There is also no tagging-adoption tracker, so whether nonprofits tag their links at all remains unknown.
