The problem

The answer today is "ask an engineer", which works, costs that engineer twenty minutes, and teaches the asker nothing reusable. Across every new PM, every incident and every "which team owns this?", that adds up.

The risk is a diagram that looks authoritative and is quietly wrong, because a map built from guesses gets trusted and then sends someone to the wrong repo mid-incident. So the design constraint is to be useful without pretending to be the source of truth, and to say which it is on every screen.

What was done

Five tools over one inventory, each answering a different question a newcomer actually asks — in the order they ask them.

ToolThe question it answersHow it works
System map"How does data move through GoFundMe?"Ten repo clusters wired the way data actually flows — donor screens and native apps, through services and event streams, into the warehouse and back out as insight. Clusters open; edges explain what travels along them; four journeys trace end-to-end.
Analytics"What shape is this org in?"Cluster sizes, where the active work is, which languages dominate each layer, and how fresh the codebase really is — all computed from the inventory rather than asserted.
Wayfinder"Where do I look?"A decision tree. Answer two questions, get a short curated list of starting repos — the path a patient senior engineer would walk you down.
Triage"What broke?"Describe it the way you would in Slack — paste the URL, name the button, mention the feature — and get the most likely repos, why each matched, and the team to ping. Rule-based pattern matching over URLs and feature language, with weighted scores.
Explorer"Show me everything."All 1,202 repos, searchable by name and description, filterable by cluster, language and status. Each row opens details, the GitHub link, and where known the owning team with a Slack ask-channel and Jira board.

What it does not cover

It is inferred from GitHub metadata, and says so on every screen

Names, descriptions, primary languages and timestamps, and nothing else. No import graphs, no service-mesh traces, no runtime call data. The guide describes itself as "an orientation map for PMs, not a confirmed architecture diagram" and tells the reader to confirm wiring with the owning team. Keep that framing in any future edit.

The edges are plausible, not measured

Every connection on the system map carries a confidence marker, and the honest reading of "high" is obviously true from the names involved rather than verified. Frontend calling backend APIs is safe. Which specific services a given repo talks to is not something metadata can answer.

271 repos are unplaceable, and 101 of them are live

Not a gap in the tool so much as a finding about the estate: a fifth of the org's repositories do not describe themselves well enough to be categorised. The guide surfaces this as "a good list to ask an engineer about", which is the right move, but nobody has worked through it.

Ownership covers 114 of 1,202 repos, and only 40 are documented

That is 3% of the estate with a citable owner. For the rest the guide points at each repo's CODEOWNERS and terraform-github's repos.json — the actual permission source of truth — which is the correct answer but not a fast one.

It is a snapshot with no refresh mechanism

Inventory as of 2026-06-30, ownership as of 2026-07-02. Nothing recomputes it. Given a third of the active estate moves within 30 days, the cluster counts and freshness figures decay quickly, and the ownership data decays faster because migrations are ongoing — two of the guide's own sources are migration notes.

The triage tool has never been tested against real incidents

The rules match URL patterns and feature language onto weighted repo lists. Whether the top suggestion is right when someone pastes a genuine Slack complaint is unmeasured, and that is the feature people will judge it on.

Pick this up next

1
Give it an internal URL
It runs in this page and the source is in the repo, so it no longer depends on a file on a laptop. It still needs somewhere an engineer can link to during an incident: a Confluence attachment, an internal static host, or a repo with Pages.
2
Make the inventory regenerable
A script against the GitHub API that rebuilds the repo list, clusters and freshness figures turns a decaying snapshot into something that stays true. The cluster rules already exist in the file; they just need to run on a schedule rather than once.
3
Convert inferred ownership to documented
73 inferred and 1 contested. Reading CODEOWNERS and terraform-github/repos.json for the repos that appear in the four journeys would upgrade the ones people actually hit, without doing all 1,202.
4
Test the triage tool on real complaints
Take twenty genuine bug reports from Slack, run each through it, and record whether the right repo appeared in the top three. About a morning's work, and it is the only way to know if the tool works.
5
Triage the 271 unclassified
Start with the 101 that are actively being pushed to. Anything actively maintained but undescribable is also the thing nobody can hand over.
