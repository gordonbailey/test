The problem

A product manager gets told something is broken and faces 1,202 code repositories with no map. The answer today is "ask an engineer" — which works, costs that engineer twenty minutes, and teaches the asker nothing they can reuse. Multiply that by every new starter and every outage.

The danger is a map that looks authoritative and is quietly wrong. A guess that gets trusted sends someone to the wrong place during an outage. So the rule was: be useful without pretending to be the source of truth, and say which one it is on every screen.

What was done

Five tools over one list of repositories, each answering a question a newcomer actually asks, in the order they ask it.

ToolThe question it answersHow it works
System map"How does data move through GoFundMe?"Ten groups of repositories, wired the way data actually moves — from the screens a donor sees, through the services behind them, into the warehouse and back out. Four journeys are traced end to end.
Analytics"What shape is this org in?"How big each group is, where work is actually happening, and how old the code is. All calculated, not asserted.
Wayfinder"Where do I look?"Answer two questions, get a short list of places to start — the path a patient senior engineer would walk you down.
Triage"What broke?"Describe it the way you would in Slack — paste the URL, name the button, mention the feature — and get the most likely repos, why each matched, and the team to ping. Rule-based pattern matching over URLs and feature language, with weighted scores.
Explorer"Show me everything."All 1,202 repos, searchable by name and description, filterable by cluster, language and status. Each row opens details, the GitHub link, and where known the owning team with a Slack ask-channel and Jira board.

The ten groups, the four journeys and the wiring between them are all in the frame above.

Ownership, and how confident each answer is

114 of the 1,202 repos have an owning team attached, each with its confidence stated rather than implied.

Three confidence levels, and what each means for a reader
ConfidenceReposWhat it means for the reader
Documented40Traced to a written source — the service catalog, Confluence, or a Slack ownership thread. Usable as-is.
Inferred73Deduced from naming and cluster. The guide asks you to verify via CODEOWNERS before acting on it.
Contested1Sources disagreed. Flagged rather than resolved by picking a winner.

Where ownership is known, the Explorer gives the team's Slack ask-channel and Jira board — so the output of "what broke?" is a place to ask, not just a repo name. 30 teams across 9 tribes: Consumer Experience, Incubation, Platforms, Payments, NPO Experience, P2P & Events, Data, Site Reliability and Design Systems.

Every source is cited on the guide itself, so any confidence level can be checked: the service catalog, four Confluence pages and two Slack threads.

What it does not cover

It is built from repository data, and says so on every screen

Names, descriptions, languages and timestamps. Nothing about what actually calls what at runtime. The guide calls itself "an orientation map, not a confirmed architecture diagram" and tells you to confirm with the owning team. Keep that framing in any future edit.

The connections are plausible, not proven

Every line on the map carries a confidence marker, and the honest reading of "high" is obviously true from the names rather than verified. Which specific services a repository talks to is not something this data can answer.

271 repositories could not be placed, and 101 are live

Less a gap in the tool than a finding about the estate: a fifth of the repositories do not describe themselves well enough to sort. The guide lists them as "worth asking an engineer about". Nobody has worked through them.

Only 40 repositories have a documented owner

That is 3% of the estate with an owner you could cite. For the rest, the guide points at where to look, which is correct and slow.

It is a snapshot with nothing to refresh it

A third of the active estate moves within 30 days, so the counts go stale quickly and the ownership data goes stale faster.

The "what broke?" tool has never been tested on a real outage

Whether the top suggestion is right when someone pastes an actual complaint is unmeasured. That is the feature people will judge it on.

Pick this up next

1
Give it an internal URL
It runs in this page and the source is in the repo, so it no longer depends on a file on a laptop. It still needs somewhere an engineer can link to during an incident: a Confluence attachment, an internal static host, or a repo with Pages.
2
Make the inventory regenerable
A script against the GitHub API that rebuilds the repo list, clusters and freshness figures turns a decaying snapshot into something that stays true. The cluster rules already exist in the file; they just need to run on a schedule rather than once.
3
Convert inferred ownership to documented
73 inferred and 1 contested. Reading CODEOWNERS and terraform-github/repos.json for the repos that appear in the four journeys would upgrade the ones people actually hit, without doing all 1,202.
4
Test the triage tool on real complaints
Take twenty genuine bug reports from Slack, run each through it, and record whether the right repo appeared in the top three. About a morning's work, and it is the only way to know if the tool works.
5
Triage the 271 unclassified
Start with the 101 that are actively being pushed to. Anything actively maintained but undescribable is also the thing nobody can hand over.
